# アウトライナー — 安定した行IDと写真の置き方の設計監査（2026-09-25）

> 状態（2026-09-25更新）：**人間の判断により、Stage 1（安定した行IDだけ）を実装済み** — `docs/OUTLINE_STABLE_ROWS.md`。写真は案A（独立した行、PhotoRow）をStage 2として、人間の確認の後に進める。ズームの起点のクラッシュ（§5の1件目）はStage 1の前提として修正済み。§5の残り3件は別件。
> 依頼（2026-09-25）：アウトライナーの写真は、本文に内部マーカーを埋める方式（`![写真](photo:…)`行）を採用しない。まず安定したnode / row IDを持たせる設計が可能かを監査し、最終的に「写真を独立したOutlineNodeとして持つ」か「特定のOutlineNodeにPhotoBlockを結びつける」かを比較する。設計が固まるまで実装しない。
> 前提：Memo（Room 26）と日記（Room 27）は「順序付きの行（block）がRoomの正本、`body`はprojection」の方式（`docs/MEMO_CONTENT_BLOCKS.md`、§11）。

## 0. 結論

- **安定した行IDは持てる。本文にマーカーを入れずに。** アウトラインの各行をRoomの表の行（`outline_nodes`）にし、それを正本、`memos.body`をその並びを文字にしたprojectionにする — Memo / 日記と同じ形。アウトラインは`serialize(parse(t)) == t`（1文字も変わらない往復）がテストで保証されているので、**既存のアウトラインは本文を1文字も変えずに行の表へ移せる**。本文を読む箇所（検索・AI・読み上げ・書き出し・複製・プレビュー・カレンダー・リンク）は**何も変えない**。
- データの変更：**Room 27 → 28、Backup 21 → 22**（表の追加と既存アウトラインの変換）。
- 写真の置き方の比較（§3）では、**写真を独立した行（OutlineNodeの一種）として持つ方が安全**と判断する。行に結びつける方式は、結びつけた行が消える・結合される・分割されるときの規則が暗黙になり、写真が消えるか、意図しない行に付いて回る危険がある。
- 順番の提案：**① 安定した行IDだけを先に入れる**（写真なし。アウトライナーの見た目・操作は変えない）→ full gateと実機確認 → **② その上に写真の行を足す**。①だけでも、折りたたみ・ズーム・スクロール位置が「行の文字を直すと外れる」問題が直る。

## 1. 今の形（事実）

- アウトラインは`memos.body`（kind = outline）の文字だけ。`OutlineText.parse`が1行ずつ`OutlineNode`（字下げ・記号・文字）か`OutlineBlank`（空行）にし、**idを読み込むたびに1..nで振り直す**（`OutlineText.kt:93-97`）。`serialize`はidを書かない。**保存をまたいで残るidは無い。**
- 編集画面（`OutlinerSession`）のidは、その画面が生きている間だけ有効。画面の作り直し（回転・process death・開き直し）や、外から本文が変わったとき（閲覧モードのタスクのチェック、分割表示の本文ペイン、AIの追記）には全行を読み直し、idが振り直される。そのとき折りたたみ・ズーム・Undoも消える。
- 画面をまたいで覚える折りたたみ・ズーム・スクロール位置は、**行の文字のhash**（深さ＋文字＋同じ行の何番目か、`OutlineFoldKeys`）でDataStoreに保存している。行の文字を直すとhashが変わるので、たたんだ見出しは黙って開き、上に同じ文字の行を足すと別の行がたたまれることがある。
- 本文を書く箇所（すべて本文まるごとを書く）：アウトライナーの保存（600msごと、1打鍵ごとに全文serialize）、AIの作成と追記（末尾に項目を1つ）、閲覧モードのタスクのチェック、分割表示の本文ペイン（生の文字で編集、400ms）、複製、テンプレートの挿入（アウトライナー内の編集として）、復元、ポータブル読み込み。
- 写真：`memo_photo_attachments`に入り、画面では一覧の上のサムネイル列。本文の中の位置は無い。

## 2. 安定した行IDの設計

### 2.1 保存
- 表`outline_nodes(memoId → memos CASCADE, nodeId, position, indent, marker, text, type)`。主キーは`(memoId, nodeId)`。`nodeId`はそのアウトラインの中で一意な数（アプリ全体では一意でなくてよい）。`type`は`line` / `blank`（②で`photo`を足す）。
- **正本は行、`memos.body`はprojection**（`text`の行を順に`indent + marker + text`でつなぐ。今の`serialize`そのもの）。書くのは新しい`OutlineStore`だけで、行と同じtransactionでbodyを書く（Memo / 日記と同じ）。
- idの割り当て：編集画面が「保存されている最大のnodeId＋1」から数え、**戻らない**（Undoで行が消えても番号は再利用しない）。これで今ある「Undoで`nextId`が戻り、後で作った行が消した行のidを再利用する」問題も消える。

### 2.2 変換（Room 27 → 28）
- 各アウトラインの本文を`parse`した結果をそのまま行にする（nodeId 1..n）。`serialize(parse(t)) == t`なので、projectionは今の本文と**1文字も変わらない**。既存の行は変えない。Memo・日記には触らない。

### 2.3 アウトライナーの保存と読み込み
- 開くとき：本文ではなく行の表から`OutlineDocument`を作る（idは保存されたnodeId）。
- 保存：`OutlineDocument`と保存済みの行を比べ、足された行・変わった行・消えた行だけを書く（1000行でも差分は数行）。projectionのbodyは今と同じく全文。
- Undo / Redo：今と同じ「文書まるごとの写し」。写しの行にはnodeIdが付いているので、戻すと同じidの行が戻る。
- 折りたたみ・ズーム・スクロール位置：文字のhashではなく**nodeId**で覚えられる（文字を直しても外れない）。保存先は今と同じDataStore（バックアップの外）。

### 2.4 本文まるごとを書く箇所（行の表を知らない書き手）
- AIの追記・閲覧モードのタスクのチェック・分割表示の本文ペイン・復元（≤21）・ポータブル読み込み：新しい本文を**行単位の差分**で行の表に載せる（Memoの`reconcile`の行版）。変わらない行はidを保つ。1行の中だけが変わった行はidを保つ。足された行は新しいid。消えた行は消える。
- これで「外から本文が変わると全行のidが振り直され、折りたたみ・ズーム・Undoが消える」も直せる（今は閲覧モードのタスクのチェック1回でも起きる）。
- 複製：行ごと写す（新しいアウトラインは同じnodeIdでよい。memoIdが違うので衝突しない）。

### 2.5 Backup 22
- `outlineNodes`を運ぶ。22のファイルは検証（アウトラインに属する、nodeIdが一意、position 0..n-1、typeの形）、bodyは行から作り直す。1〜21のファイルは本文を`parse`して作る（変換と同じ）。

### 2.6 危険と対策
- **1打鍵ごとの保存**：今も全文をserializeしている（1000行で250ms以内のテストあり）。行の差分は小さいので、書く量は今より少ない。1000行のアウトラインで保存時間を測るテストを足す。
- **外からの書き込みとの取り合い**：今でもアウトライナーは開いている間に外で本文が変わっても気づかず、自分の保存で上書きする（最後に書いた方が勝つ。§5）。行の表にしても同じ。これは別件として扱う。
- 本文の読み手は変わらないので、行の表の不具合は「アウトライナーの画面」と「差分の載せ方」に閉じる。

## 3. 写真の2案

### 3.1 案A：写真を独立した行として持つ（`type = photo`、`attachmentId`、`indent`）
- 写真は行の並びの中の1行。字下げを持ち、字下げ・上下移動・ドラッグ・折りたたみ・ズームで**項目と同じに**動く（親の項目を動かせば子の写真も付いて動く）。
- projection（body）には**写真の行を出さない**。本文を読む箇所は何も変えない（本文に内部マーカーを入れないという判断どおり）。
- 閲覧モード：Memoと同じく、写真をbodyの行と行の間に差し込む（`MemoReadingView.photoBreaks`）。
- 編集：Memoと同じ規則（caretの位置で項目を分けて写真の行を入れる／Backspaceでは写真を消さない／写真は右上の⋮で削除・フルスクリーン・写真一覧）。
- 必要な作業：`OutlineEditing`の各操作が写真の行を扱う（文字の結合・分割・テンプレート挿入で写真の行に文字が混ざらない、タスクのチェックは写真の行を数えない、折りたたみの範囲は字下げで決まるので自然に含まれる）。外からの書き込みの差分では、写真の行は本文に出ていないので、前後の文字の行に付いて位置を保つ（Memoの`reconcile`と同じ考え方）。

### 3.2 案B：特定の項目にPhotoBlockを結びつける（`outline_node_photos(memoId, nodeId, attachmentId, order)`）
- 写真は項目の下に表示される。項目のidが安定していれば、字下げ・移動・ドラッグでは付いて動く。
- ただし次の場合の規則がすべて暗黙になる：
  - **項目が消える**（Backspaceで上の行に結合、行を消す）→ 写真を消すのか、上の項目に移すのか。消せば**写真が黙って消える**。移せば、ユーザーが置いた場所と違う項目に付く。
  - **項目を分割する**（caretの途中でEnter）→ 写真は前半・後半のどちらに付くか。
  - **項目の前（アウトラインの先頭）や、項目と項目の間の「どれにも属さない位置」**に写真を置けない。
  - **Undo**：文書の写しに写真の結びつきが入っていないと、項目を消してから戻したときに写真が戻らない。写しに入れれば、それは案Aと同じ情報を別の場所に持つことになる。
- 外からの書き込みで項目の文字が大きく変わると、写真がどの項目に付くかが変わりうる。

### 3.3 比較

| | 案A 写真の行 | 案B 項目に結びつける |
|---|---|---|
| 位置が明示されているか | はい（並びの中の1行） | 項目の下に限られる |
| 項目の削除・結合 | 写真は残る（Backspaceは写真を消さない） | 消すか移すかの規則が要る。**消えれば気づかれずに失われる** |
| 項目の分割 | 分割した所に入る | どちらに付くかの規則が要る |
| Undo | 文書の写しに入っているので戻る | 別に持たないと戻らない |
| 本文を読む箇所 | 変更なし（projectionに出さない） | 変更なし |
| 編集操作の変更 | 各操作が写真の行を扱う（量は多いが規則は明示的） | 操作はほぼそのままだが、削除・結合・分割に写真の付け替えを足す |
| Memo / 日記との一貫性 | 同じ（写真は内容の1ブロック） | 違う |

→ **案Aを推奨。** 作業量はやや多いが、写真が黙って消える・別の場所へ移る経路が無く、Undoも今の仕組みのまま効き、Memo・日記と同じ「写真は内容の1ブロック」になる。

## 4. 作業の見積もりと順番（承認されたら）
1. **安定した行ID**：`outline_nodes`、Room 28、Backup 22、`OutlineStore`、行単位の差分、アウトライナーの読み込み・保存の切り替え、折りたたみ・ズーム・スクロールをnodeIdで覚える。見た目は変えない。full gateとS20確認。
2. **写真の行（案A）**：`type = photo`、編集操作、閲覧モードの差し込み、⋮メニュー、caretでの挿入。写真の行を足しても本文は変わらない。ただし行の種類が増えるので、1の版（22）の読み手が`photo`の行を知らずに落とさないよう、Backupの版をもう1つ上げるか、1の時点で`photo`を検証に含めておくかを、その段階で判断する。full gateとS20確認。

## 5. 監査で見つけた以前からの問題（今回は直さない。別件として記録）
- **ズームの根の行が消えると落ちる可能性**：ズーム中の根の行をBackspaceで消す、またはその行を作った操作をUndoすると、`OutlineEditing.position()`の`require`が失敗しうる（テストなし、`OutlineEditing.kt:338-341, 474-478`）。
- **ポータブル書き出しのアウトラインを読み込むとメモになる**（kindを運ばない。`PortableImportEngine.kt:105-109`）。
- **アウトライナーを開いている間の外からの書き込みは上書きされる**（分割表示の本文ペインやAIの追記が、開いているアウトライナーの次の保存で消える。`updatedAt`の確認なし）。
- **閲覧モードでタスクを1つチェックすると、全行のidが振り直され、折りたたみ・ズーム・Undoが消える**（外からの書き込みとして読み直すため。§2.4で直せる）。
- 日記のAI追記と復元のロック順（`docs/PHOTO_PLACEMENT_DIARY_OUTLINE.md` §1.6）— 別件のconcurrency fixとして予定どおり。
