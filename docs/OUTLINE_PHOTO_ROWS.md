## 0. 結論

**今のschemaでは写真の行を安全に表せない。Room 28→29、Backup 22→23が要る。** 理由は§1。それ以外の設計（§2〜§5）はStage 1の上にそのまま載る。

## 1. schemaの変更が要る理由

`outline_rows(memoId, rowId, position, text)`には、行が写真であることと、どの写真かを持つ場所が無い。今の列で表す方法は2つしかなく、どちらも採れない。
- **`text`列に印を入れる**（例：見えない文字の後に写真のid）：本文に内部マーカーを入れないという判断は、行の表の中でも同じ理由で当てはまる。さらに、Stage 1の版（Room 28、S20に入っている）で同じDBを開くと、印の行も文字の行として本文のprojectionに混ざるか、projectionが本文と違うため本文から行を作り直して**写真の行が黙って消える**。同じRoomの版のまま、行の意味だけを変えることになる。
- **別の表（`memo_content_blocks`など）に置く**：写真と文字が2つの表に分かれ、1つの並び（position）を共有できない。並べ替え・字下げ・Undoのたびに2つの表を合わせることになり、Stage 1の「行の表が正本」が崩れる。

→ `outline_rows`に**`kind`（'text' / 'photo'）と`photoAttachmentId`**を足す。写真の行は`memo_photo_attachments`の行を指す（そのアウトラインの写真だけ、1枚につき1行、FK・unique）。SQLiteでは外部キーを`ALTER TABLE`で足せないため、移行は表を作り直して行を写す（文字の行は1文字も変えない）。Backupも、写真の行を運ぶ形が変わるので23にする（22の読み手に写真の行を黙って落とさせないため — 日記・Memoのときと同じ判断）。

## 2. データの形（案）

- `outline_rows(memoId, rowId, position, kind, text, photoAttachmentId)`。文字の行は今と同じ（`kind = 'text'`、`text`は行の文字そのまま）。写真の行は`kind = 'photo'`、`text`はその行の**字下げだけ**（深さを文字の行と同じ規則で持つ）、`photoAttachmentId`はその写真。
- **写真の行は自分のstable idを持つ独立した行**。文字の行を消しても、分割・結合しても、写真の行のidと存在は変わらない（添付ではない）。
- **projection（`memos.body`）には写真の行を出さない**。文字の行だけを今と同じ形でつなぐので、写真を足しても本文・検索・AI・読み上げの内容は変わらない。
- 画面の中では、写真の行は深さを持つ行として扱う（`OutlineEntry`の新しい種類。空の文字の行と同じ木の規則：字下げ・上下移動・ドラッグで項目と同じに動き、親を折りたたむと隠れ、ズームの中にあれば見え、外なら見えない）。**ズームの起点にはしない**（文字の行だけ）。

## 3. 編集

- 写真を追加：今選んでいる文字の行の**すぐ後ろに、同じ深さで**写真の行を入れる（複数なら選んだ順）。先頭・末尾へは集めない。caretが行の途中なら、Memoと同じく行をそこで分けてから間に入れる。
- 写真の行の操作：右上の⋮から フルスクリーン / 上へ / 下へ / 削除（Outlinerは行の移動が既にあるので上へ・下へを残す）。字下げ・字下げ解除・ドラッグは項目と同じ。
- Backspaceは写真の行を消さない（上の行と結合するときは写真の行を飛ばして、上の文字の行へ）。Enterは写真の行から始まらない。
- **Undo / Redo**：写真の挿入・削除・移動・字下げは文書の写しに入るので、そのまま戻る。**写真のファイルはUndoの間は消さない**：写真の行を消しても、その写真（`memo_photo_attachments`とファイル）はすぐには消さず、アウトライナーを閉じるときに、どの写真の行からも指されていない写真だけを消す（孤立した写真を残さない）。途中でアプリが終わった場合は、次に開いたとき、行の無い写真を先頭の写真の行として戻す（消さない側に倒す）。
- 古い画面による上書きの禁止（§9、Stage 1で入れた版の確認）は写真の行にもそのまま効く。

## 4. 変換（Room 28→29）

- 写真の無いアウトライン：行・id・本文・見た目は一切変えない（`kind = 'text'`になるだけ）。
- 写真のあるアウトライン（今はサムネイルの列で上に並んでいる）：その写真を**先頭の写真の行**（深さ0、`sortOrder`の順）にする。今の見た目（写真が上）に一番近い。文字の行のidと本文は変えない。写真の行のidは、そのアウトラインの最大のid＋1から。

## 5. 周辺

- 閲覧モード：写真を行と行の間に大きく出す（Memo / 日記と同じ`MemoReadingView.photoBreaks`）。
- 書き出し：プレーンテキストは写真を除く。Markdown（ポータブル書き出し）は、今の写真の書き出し規則のまま、写真の行の位置に画像への参照を出せる（本文には書かない）。
- Backup 23：写真の行（`kind`、`photoAttachmentId`）を運ぶ。検証：写真の行はそのアウトラインの写真を1回ずつ指す、そのアウトラインの写真は必ずどれかの写真の行に指される。1〜22のファイル：写真を先頭の写真の行にする（変換と同じ）。
- 通常の画面に「写真 N枚」は出さない。写真は本文幅・比率を保つ・切り取らない・キーボード中もサムネイル列に戻らない（Memo / 日記と同じ）。

## 7. 実装の記録（2026-09-25、人間の判断：§6の1〜4すべて承認）

人間の判断（そのまま）：Room 28→29、Backup 22→23（写真の行の種類・位置・写真の参照はポータブルな文書の内容そのもの）。既存の写真は先頭の写真の行。写真の行の削除では**ファイルをすぐ消さない**：行はsessionの中で消え、写真とファイルは残り、Undoで戻せる。editor / sessionが終わるとき、**最後に保存された状態で、その写真を指す行が0**のときだけ物理削除する。「editorを閉じた」だけでは消さない — **DBで参照0 / 保存が成功している / Undoのsessionが終わっている** を確かめてから。保存の失敗・conflictのときは消さない。process deathでは、失うより孤立を残す側に倒す（積極的な掃除はしない）。写真の行の上へ / 下へは残す。

### 7.1 データ

- `outline_rows(memoId, rowId, position, kind, text, photoAttachmentId)`（Room 29）。`kind`は`'text'` / `'photo'`。写真の行の`text`は字下げだけ、`photoAttachmentId`は`memo_photo_attachments`の行（FK、`ON DELETE CASCADE`、unique）。写真が消えれば行も消える — 孤立した行は残らない。
- `OutlineNode.photoAttachmentId`：写真の行は`OutlineNode`（marker・文字なし、字下げで深さ）。`OutlineText.serialize` / `OutlineRows.projection`は写真の行を出さない — `memos.body`は文字の行だけ。検索・AI・読み上げ・書き出し・プレビューが読む本文は変わらない。
- `OutlineStore.write`：写真の行はその**アウトライン自身の**写真だけを指す（他のメモの写真を指す行は書かない）、1枚に1行（2行目は`require`で拒否）、写真の`sortOrder`は行の順（どの行も指さない写真はその後ろ）。
- **`MIGRATION_28_29`**：表を作り直す（FKは`ALTER TABLE`で足せない）。文字の行はidと文字を1バイトも変えず`'text'`、位置だけその写真の数だけ下へ。写真は先頭に`sortOrder`順、深さ0、idはそのアウトラインの最大のid＋1から。写真の無いアウトラインは変わらない。メモの写真は行にならない。
- **Backup 23**：`OutlineRowBackupDto`に`kind`（既定`"text"`）と`photoAttachmentId`。23は行をそのまま戻す（写真の行も）。22は行とidをそのまま、写真を先頭の写真の行に。1〜21は本文から行を作り、写真を先頭に。検証（`INVALID_OUTLINE_ROWS`）：未知の種類、写真の行に文字、写真の無い写真の行、文字の行に写真、そのアウトラインの写真でないもの、1枚を2行 — は拒否。どの行も指さない写真は許す（開いたときに先頭へ戻る、§7.3）。

### 7.2 編集

- 写真を追加：`OutlineEditing.insertPhotos` — caretが文字の途中なら行をそこで分けて間に、行頭なら行の前（同じ深さ）、それ以外（行末・caret無し）は行のすぐ後ろ（子がある行なら最初の子）に入れ、その後ろに同じ種類の空の行を足して、そこで書き続ける。複数は選んだ順。先頭・末尾へは集めない。すでに行のある写真は2回入れない。
- 写真の行の⋮：フルスクリーン / 上へ / 下へ / **字下げ / 字下げを戻す** / 削除。写真の行はcaretを持たないので、字下げはツールバーではなく⋮から（人間の判断 2026-09-25：残す — Outlinerでは深さそのものが文書の構造）。上へ・下へ・字下げは文字の行と同じ`moveUp` / `moveDown` / `indent` / `outdent`（子を連れて動く）で、できない位置では文字の行のツールバーと同じ`canMoveUp` / `canMoveDown` / `canIndent` / `canOutdent`で**無効**になる（写真の行だけの例外規則は作らない）。フルスクリーンと削除はいつでも。
- 写真の行は文字を持たない：`updateText` / `replaceText` / `split`は何もしない。Backspaceは写真の行を消さず、写真の行を越えて結合しない（写真のすぐ下の行頭のBackspaceは何もしない）。
- **写真の行は親にならない**：`ancestors`（パンくず・一つ上へ・ズームの逃げ先・rail）は写真の行を飛ばす、`nodesWithChildren`は写真を親に数えない、`toggleFold`は写真を折りたたまない、`zoomInto`は写真の行に立たない（ズームの起点は文字の行だけ）。写真の行は親を折りたたむと隠れ、ズームの範囲の中なら見え、外なら見えない。fold keyは写真の行を数えない。
- Undo / Redo：挿入・削除・移動・字下げは文書の写しに入るので戻る。同じidで戻る。一度使ったidは使い回さない（`idFloor`）。
- 表示：本文幅・比率を保つ・切り取らない（`InlinePhoto`）。サムネイルの列（strip）は無くなった。通常の画面に「写真N枚」「N/20枚」は出さない。閲覧モードは行と行の間に写真（`outlinePhotoBreaks` → `MemoReadingView.photoBreaks`）。
- 古い画面による上書きの禁止（`docs/OUTLINE_STABLE_ROWS.md` §9）はそのまま写真の行にも効く：conflictの間、写真の行は動かず（`session.writable`）、何も書かれない。再読み込みで同じ本文・違う写真の行の版を読んだときも、セッションはそれを別の版として受け取る（`acceptBody`は本文だけでなく行も比べる。自分のechoは何も変えない）。

### 7.3 写真のファイル

- 写真の行を消す：sessionの中で行が消えるだけ。自動保存で行の表からも消えるが、`memo_photo_attachments`の行とファイルは**残る**（Undoで戻せる）。
- **手放すのはoutlinerを離れるとき（`saveAndThen`）だけ、しかも次をすべて満たすとき**（`MemoEditorViewModel.releaseUnshownOutlinePhotos`）：outlineである、conflictでない、保存が済んでいる（`contentRevision == savedRevision`：保存の失敗・未保存の文字があれば手放さない）、置く途中の写真が無い。そのとき、DB上で**どの写真の行にも指されていない写真だけ**（`OutlineRowDao.unshownPhotos`）を1つのtransactionで消し、その後`garbageCollect`がどこからも参照されないファイルだけを消す。写真の行が指す写真は決して消さない。
- **process death**：写真を入れた直後や、消して保存した直後にprocessが終わると、どの行も指さない写真が残る。次に開いたとき（`OutlineStore.materialize`）、その写真は**先頭の写真の行として戻り、書き込まれる** — 見ないまま手放されることは無い（消した写真が戻ることはある。失うより残す）。
- 同じ写真をもう一度追加：このsessionで消したが、まだ手放していない写真なら、「追加済み」と断らず、その写真を書いている場所へもう一度出す（`PhotoImportResult.duplicateIds` → `OutlinePhotos.toPlace`）。新しい記録は作らない。**写真の行としてまだ見えている写真**なら、これまでどおり「同じ写真は追加済みです」。

#### 7.3.1 20枚の上限は「見えている写真」だけを数える（人間の判断 2026-09-25）

分けて考える2つ：**A** 元に戻すのために記録とファイルを持っている写真（消した写真、手放す前の写真、process deathから戻る候補）と、**B** いまアウトラインに写真の行として見えている写真。**上限はBだけを数える**（`OutlinePhotos.activeCount` = 文書の写真の行 ＋ これから置く写真）。取り込み（`AttachmentRepository.importMemoPhotos(activeCount = …)`）はこの数で空きを決める — メモ・日記は今までどおり記録の数。例：20枚見えている → 1枚消す → 19枚 → 新しい写真を1枚追加できる（記録は21件、うち1件はAとして残り、離れるときに規則どおり手放される）。Aのファイルの扱い（§7.3）は変えていない。

**元に戻す / やり直しと上限（監査）。** Outlinerの元に戻すは、文書全体の写しを1段ずつ戻す。19枚＋消した1枚＋新しい1枚＝20枚のとき、元に戻すはまず**新しい写真**を取り消し（19枚）、次に消した写真を戻す（20枚）— 1段ずつ戻る限り、実際にあった状態にしか戻らないので21枚にはならない。それでも、上限を越えていた状態（process deathから先頭に戻った写真で21枚だった、など）へ戻る段はありうるので、`OutlinerSession.undo` / `redo`は**上限を越え、かつ今より多くなる段を実行しない**（`HistoryStep.PHOTO_LIMIT`）：文書も保存も変わらず、その段は残り、画面に「写真は最大20枚までです。追加した写真を減らしてから元に戻してください。」と出す（黙って失敗しない）。今見えている写真を勝手に消して場所を作ることはしない。写真を1枚消せば、元に戻すはまたその新しい段から進められる。

**バックアップ。** 23の検証の「1件の記録につき写真20枚まで」は、アウトラインでは**写真の行の数**で数える（Aの記録は数えない。見えている写真が20枚でAを持つアウトラインのバックアップが、自分の検証で断られないように）。メモ・日記と22以前のファイルは今までどおり記録の数。

## 8. 何も書かずに閉じた新しいアウトライン（人間の判断 2026-09-25）

- **呼び名**：題の無いアウトラインは「無題のアウトライン」ではなく**「無題のアウトライナー」**（一覧のカード、コピーの名前「無題のアウトライナーのコピー」、チャット・検索が使う`DocumentTitles.UNTITLED_OUTLINE`）。
- **作られなかったことにする**：メモは何か書くまで保存されないが、アウトライナーは開くために＋の時点で行を作る。そこで、**＋で作ってそのまま開いたアウトライナー**（routeの`fresh`引数。process deathをまたいでも残る）を離れるとき（`saveAndThen`）、中に何も無ければ、そのアウトラインを消す — 作られなかったものとして。
  - 条件（`MemoEditorViewModel.discardEmptyNewOutline`）：outlineである、conflictでない、すべて保存済み（`contentRevision == savedRevision` — 画面の文字がまだ保存されていなければ消さない）、置く途中の写真が無い。
  - もう一度、1つのtransactionで確かめる（`OutlineStore.discardIfEmpty`）：アウトラインで、アーカイブ・ゴミ箱・ノートの回でなく、題が無く、**どの行にも文字が無く**（記号だけの行・空の行は文字ではない）、写真の行も写真の記録も無く、コメントもタグも無い。1つでもあれば消さない。消すと行（`outline_rows`）も一緒に消える（CASCADE）。
  - 写真を足して消した場合：離れるときにまず手放す規則（§7.3）で写真が手放され、そのあと空なら消える。
  - **もとからあったアウトラインは、開いて閉じても消えない**（`fresh`は＋からだけ）。S26などに以前のbuildで作られた空のアウトラインが残っていても、自動では消さない（利用者のデータを勝手に消さない）。
  - メモとの違い：メモは「一度も保存されなかった」ものが残らない。アウトライナーは、同じ訪問の中で書いて全部消した場合も、離れるときに何も無ければ残らない。
