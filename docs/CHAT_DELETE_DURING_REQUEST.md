# 実行中の依頼の会話を削除すると落ちる — 修正（2026-09-26）

> 状態：**実装済み、マージ前で停止。** ブランチ`fix/chat-delete-during-request`（base：Human UI/UX Reviewの基準`integration/v1-feature-freeze` `a7778ca`）。Human Review中に見つかった、別件のsafety bug。`feature/chat-memo-context`（`3706575`、完成・固定）とは混ぜていない。Room 29 / Backup 23 / versionCode 4 / 1.1.0 / prompt / grammarは変えていない。

## 1. 監査 — 実際の経路

1. **依頼の開始**：`ChatViewModel.askText`（と確認の質問への答え`answerClarification`）が`ensureConversation`で会話のidを決め、利用者の行を書き、そのidを持ったまま中断する（Fast Path / DecisionEngineは数ms、モデルは数秒〜）。
2. **返答**：`showResult`が同じidで`setLatestResults` / `setAnchor` / `append(ASSISTANT)`を書く。会話がまだあるかは誰も確かめていなかった。
3. **削除**：経路は3つ。ドロワー（`deleteConversation` — busyでも止めない）、「履歴を管理」の1件（別の画面が`store.delete`を直接呼ぶ — チャットのViewModelと`askJob`はback stackで生きている）、「すべて削除」（`deleteAll`）。どれも走っている依頼を止めない。
4. **落ちる**：`chat_messages`と`chat_result_refs`はCASCADEの外部キーを持つので、遅れた`insertMessage` / `insertResultRefs`が`SQLiteConstraintException`を`viewModelScope`の中で投げ、誰も受けず、アプリが落ちる。モデル経路だけでなく、Fast Pathでも同じ（テストで再現）。
5. **監査で見つかった他のこと**：今の会話が消えると画面は新しいチャットに移る（`switchTo(null)`）が、遅れた`showResult`はその新しい画面に消えた会話の結果を出す — **遅れたプレビューはそこで確認できてしまう**（消えた会話の書く権限が残る）。`confirmWrite`はプレビューが生まれた会話ではなく、その時の会話に行を書く。

## 2. キャンセルだけでは足りない理由

- 「履歴を管理」の削除は別の画面で起き、チャットが知るのは会話一覧のFlowを通してだけ — その頃には結果はもう出ていて、書き込みが走っているかもしれない（Fast Pathは数ms）。
- キャンセルは協調的：最後の中断点を過ぎた（またはRoomの書き込みの中にいる）コルーチンは、それでも書く。
- 「すべて削除」には狙う1つの依頼がない。
- 依頼が自分の会話を記録する前の瞬間に削除が来ると、キャンセルする相手がまだいない。

だから**書く直前の確認**が要る — それも「確認してから書く」の間に削除が入らない形で。

## 3. 修正（二層、DBの例外を制御に使わない）

**ストア（最後の門）**：`ConversationStore.append`と`setLatestResults`は、会話があるかの確認と書き込みを**1つのRoom transaction**で行う（Roomの書き込みtransactionは1つずつなので、確認と挿入の間に削除は入れない）。会話が無ければ何も書かず、何も作り直さず、例外も投げない — `append`は`null`を返す。`setAnchor`は`UPDATE`なので、無い行には何もしない。

**ViewModel（依頼の身元）**：
- 依頼は自分の会話と、始まった時の画面の世代（`liveGeneration`）を持つ。結果が画面に出るのは、画面がまだその会話・その世代を見ている時だけ（会話の切り替え・削除で世代が進む）。
- 返答の行の`append`が`null` ＝ 会話は途中で消えた → 何も出さない（画面が削除をもう聞いたかどうかに関係なく、決定的）。確認の質問の行も同じ。
- 会話が消えたら（ドロワー、または一覧から消えたのをデータベースで確かめて — 古い一覧を削除と取り違えない）、その会話の走っている依頼をキャンセルする（モデルのleaseも放す）。今の会話なら画面は新しいチャットへ（結果・プレビュー・そのチケットも一緒に消える）。
- 依頼は自分の会話を記録した直後に、会話がまだあるかを確かめる — 記録の前に来た削除はここで止まる（何の仕事もしない）、後に来た削除はキャンセルで止まる。ドロワーの削除は依頼と同じmain threadで順番に処理する。
- `confirmWrite`は、プレビューの会話が消えている・もう画面に無い時、書かずにプレビューを閉じる。
- 削除はそのまま最終：削除を拒まない、会話を戻さない、依頼の終わりを待たない。遅れた依頼について何も言わない（toast / snackbar無し）、別の会話の画面にエラーも出さない。

変えていないもの：Room / Backup、prompt / grammar、AIの意図の設計、メモの選択（`feature/chat-memo-context`）— あちらの「会話の削除で選択も消す」は同じ`delete` / `deleteAll`の中にあり、統合してもそのまま両立する。

## 6. 統合（2026-09-26、HANDOFF §16.107）

`feature/chat-memo-context`（「メモを選択」）と一緒に`integration/v1-feature-freeze`へ統合した。`ChatViewModel`の衝突は、両方が同じ場所に足したフィールドの宣言だけ（両方残した）。新しい会話は「作る → メモの選択を結び付ける → 今の会話にする → 依頼が身元を持つ → 会話がまだあるか確かめる → 続ける」の順。統合で1つだけ足した：`conversationGone`は会話の「メモを選択」も消す（会話の作成と削除の間の一瞬に結び付けた選択が残らないように — ストアの削除も消すが、その前に結び付けが書かれる場合がある）。選んだメモへのAPPENDが走っている・プレビューが出ている時に会話を消しても、メモには何も書かれない（`ChatMemoContextDeleteInstrumentationTest` 3）。
